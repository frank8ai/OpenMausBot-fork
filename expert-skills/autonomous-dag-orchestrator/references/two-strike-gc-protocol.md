# 两振出局死锁熔断与生命周期垃圾回收执行协议

## 1. 两振出局死锁熔断机制 (Two-Strike Fuse Protocol)

### 为什么必须设立硬熔断？
在自主 Agent 编排系统中，当一个任务未通过测试或代码审查被打回时，初级编排往往会无休止重试。这极易陷入局部死循环，不仅消耗海量 Token 预算，还会导致整个 DAG 线程被永久死锁。

### 熔断规则与执行阶梯：
1. **Strike 1 (初次打回)**：
   - 记录具体错误堆栈与打回意见；
   - 重新路由给全栈开发，在隔离测试沙箱中进行外科手术修复；
   - 计数器 `rework_count = 1`。
2. **Strike 2 (二次打回，触发硬熔断)**：
   - 当同一任务再次被评审或质保打回（`rework_count >= 2`），触发 **Two-Strike Hard Fuse**；
   - 立即切断该节点的所有自动重试与调度；
   - 状态强制跃迁为 `BLOCKED_ESCALATED`；
   - 自动生成《死锁诊断单》，挂载打回日志、Git Diff 与前置契约，自动召集**软件架构师**与**产品战略师**进行联合会诊。

## 2. 线程生命周期垃圾回收规约 (Thread / Session GC Protocol)

### 僵尸会话的危害：
- 长期存活的临时会话会产生巨大的上下文残留，不仅导致内存泄露，还会使 LLM 在后续调用中产生跨任务幻觉污染。

### GC 标准清道夫流程 (Garbage Collection SOP):
1. **凭证核验**：确认任务状态已为 `SETTLED` 且交付物已落盘至权威目录；
2. **临时分支清理**：自动执行 `git branch -D temp/*` 与 `scratchpad` 物理删除；
3. **会话销毁**：向 OpenMausBot 发出 `close_thread` 指令，彻底释放运行时上下文句柄；
4. **台账对账**：在 DAG 日志中标记资源已回收，确保内存与 Token 处于干净的基线状态。
